# Чек-лист самопроверки перед сдачей

Пройдите список для своей нотации. Каждый пункт — типовая ошибка, за которую снимают баллы.
Три минуты здесь экономят пересдачу.

## Общее (для любой диаграммы)

- [ ] У диаграммы есть название.
- [ ] Всё, чего нет в легенде, но что пришлось решить самому, — записано в «Допущениях».
- [ ] Диаграмма отвечает на один вопрос (данные / процесс / поведение), а не на все сразу.
- [ ] Приложен исходный код диаграммы (DBML / .bpmn / PlantUML), не только картинка.

## ERD

- [ ] Таблицы — единственное число, `snake_case`; PK — `id`; FK — `<таблица>_id`.
- [ ] На каждой связи указана кардинальность с обеих сторон.
- [ ] Ни одной связи M:N «напрямую» — все разрешены связующими таблицами.
- [ ] Нет списков значений в одном поле (id через запятую, «телефоны через точку с запятой»).
- [ ] Там, где нужна история (попытки, статусы, тарифы), — отдельная таблица, а не одно поле.
- [ ] «Исторические» значения (цена, тариф на момент сделки) зафиксированы в сделке,
      а не читаются из справочника.
- [ ] Один человек в нескольких ролях не породил дублирующие таблицы с ФИО и email.
- [ ] Вычисляемые значения (средний балл, сумма) не хранятся без причины.

## BPMN

- [ ] Стартовое событие — одно на пул; названо фактом («Заявка поступила»).
- [ ] Задачи — глагол в инфинитиве + объект; события — свершившийся факт.
- [ ] Каждое завершающее событие названо исходом; исходов столько, сколько смыслов.
- [ ] После каждого шлюза-разветвления условия подписаны на потоках.
- [ ] Взаимоисключающие ветки — XOR; одновременные — AND; AND-разветвление слито парным AND.
- [ ] Между пулами — только message flow; sequence flow границу пула не пересекает.
- [ ] Всё, что происходит «по времени» (через N дней, в полночь), — событие-таймер,
      а не задача.
- [ ] Внешние участники (клиент, партнёр) не нарисованы дорожками внутри вашего пула.

## UML Use Case

- [ ] Акторы — снаружи границы системы; система очерчена рамкой.
- [ ] Ни одного актора-«базы данных» или актора-«сервера».
- [ ] Имена use case — глагол + объект, отвечают на «что актор хочет сделать?».
- [ ] include — только для обязательных включений; extend — для опциональных; направления
      стрелок проверены.
- [ ] Диаграмма не пытается показать порядок действий.
- [ ] Внешние системы (шлюзы, госсервисы) присутствуют как акторы.

## UML Activity

- [ ] Ромб — выбор одной ветки, fork/join — параллельность; они не перепутаны.
- [ ] У каждого fork есть парный join (или каждая ветка доведена до финала осознанно).
- [ ] Циклы имеют условие выхода.
- [ ] Финальных узлов столько, сколько исходов, и они названы.
- [ ] Дорожки — по ролям, а не по этапам.

## UML Sequence

- [ ] Время течёт сверху вниз.
- [ ] Вызовы — сплошные стрелки, ответы — пунктирные, асинхронные — открытый наконечник.
- [ ] У каждого alt-фрагмента условия в квадратных скобках; ветвления не нарисованы «на глаз».
- [ ] Полосы активации показывают, кто занят.
- [ ] Слои не «срезаны»: клиент не ходит в БД напрямую.
- [ ] Асинхронное действительно асинхронно (уведомления не блокируют ответ).

## DFD

- [ ] Каждый поток подписан данными-существительным.
- [ ] Нет потоков сущность→сущность и хранилище→хранилище без процесса.
- [ ] Ни одного процесса-«чуда» (без входов) и «чёрной дыры» (без выходов).
- [ ] Есть контекстная диаграмма; уровни сбалансированы (входы/выходы совпадают).
- [ ] Стрелки не читаются как порядок действий.
- [ ] Все внешние получатели данных из легенды (банк, ГИС и т.п.) присутствуют.
