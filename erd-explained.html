01Модель данных: три смысловых блока

Модель из четырнадцати таблиц целиком нечитаема, поэтому аналитики режут её на блоки по смыслу. Здесь три: деньги и доступ, расписание и записи, персональные тренировки. Связи между блоками идут через client и trainer.

Блок 1. Клиент, абонементы, посещения

Чтение Crow’s Foot: чёрточка — «ровно один», кружок с чёрточкой — «ноль или один» (связь необязательна), «лапка» — «много». Читайте связь с двух сторон: у одного клиента много карт, но каждая карта принадлежит ровно одному клиенту.

Почему именно так

  • client — один человек, один аккаунт. Роли (клиент, тренер) не порождают отдельных таблиц с дублями ФИО: тренер, который сам ходит на йогу, остаётся одной строкой.
  • membership_type — справочник, membership — экземпляр. Тип отвечает на вопрос «что бывает» (безлимит, утренний, пакет-12), карта — «что купил Иван 3 мая». Это разные уровни, их постоянно путают.
  • Цена лежит в обоих местах — и это не ошибка. В типе цена актуальная, для витрины. В карте — снимок на момент покупки: заказчик прямо сказал, что купленная карта живёт по прежним условиям.
  • freeze_period — отдельная сущность, а не флаг. Флаг is_frozen ответил бы только «заморожена ли сейчас», а нужно знать даты каждого периода: лимит 30 дней в году считается по ним, и на них же продлевается срок карты.
  • company — необязательный плательщик. Обычную карту покупает сам клиент, корпоративную оплачивает компания, поэтому связь «ноль или один», а не обязательная.
  • visit связан и с клиентом, и с картой. Только клиента мало: у человека за годы пять карт, а списывать посещение и считать возврат нужно по конкретной.

Блок 2. Тренеры и виды занятий: разрешение «многие-ко-многим»

Связь «многие-ко-многим» в реляционной БД не существует напрямую. Связующая таблица превращает её в две связи «один-ко-многим» — и заодно даёт место для собственных атрибутов связи (например, дата сертификации тренера по этому виду).

Тренер Аня ведёт йогу и стретчинг, а кроссфит ведут трое — «много» с обеих сторон. Попытка обойтись полем trainer_id в workout_type означала бы «у вида ровно один тренер», а поле type в trainer — «тренер ведёт ровно один вид». Оба варианта противоречат словам тренера на интервью.

Блок 3. Расписание и записи

Три справочника слева «собираются» в конкретное занятие расписания, а booking — связующая таблица между занятием и клиентом, у которой есть собственная жизнь: статус booked → attended / cancelled / no_show.

Почему booking обязателен. Без него запись клиента негде хранить, а вместе с ней исчезают неявки — и требование «после трёх неявок подряд блокировать на неделю» становится нереализуемым. Это типичный случай: правило из интервью умирает молча, если под него не завели данные.

Блок 4. Персональные тренировки

Пакет покупается у конкретного тренера — поэтому связь идёт и от клиента, и от тренера. Слот — отдельная строка со временем: именно на паре «тренер + время» стоит уникальное ограничение, закрывающее ту самую двойную продажу из WhatsApp.

03Полный код модели (DBML для dbdiagram.io)

Скопируйте в dbdiagram.io — схема отрисуется сама. Комментарии в коде объясняют неочевидные решения.

Table client {
  id int [pk]
  full_name varchar
  phone varchar
  email varchar
  status varchar          // active / deleted — удаляем «мягко», см. кейс 6
}

Table company {           // корпоративный плательщик
  id int [pk]
  name varchar
  inn varchar
}

Table membership_type {   // СПРАВОЧНИК: актуальная витрина тарифов
  id int [pk]
  name varchar            // безлимит / утренний / пакет-12
  price decimal(10,2)     // деньги — всегда decimal, никогда float
  visit_limit int         // null = безлимит
  time_limit_to time      // 16:00 для утреннего, null = без ограничения
  freeze_days_per_year int
}

Table membership {        // ЭКЗЕМПЛЯР: купленная карта
  id int [pk]
  client_id int [ref: > client.id]
  company_id int [ref: > company.id, null]   // 0..1 — плательщик
  membership_type_id int [ref: > membership_type.id]
  price decimal(10,2)     // СНИМОК цены на момент покупки
  visit_limit int         // снимок условий: тариф потом менялся, карта — нет
  time_limit_to time
  starts_on date
  ends_on date            // сдвигается при заморозке
  status varchar          // active / frozen / expired / refunded
  // правило: не более одной active-карты на клиента
  // (частичный уникальный индекс, на схеме не рисуется)
}

Table freeze_period {
  id int [pk]
  membership_id int [ref: > membership.id]
  starts_on date
  ends_on date            // не короче 7 дней; сумма за год <= 30
}

Table visit {             // журнал турникета
  id int [pk]
  client_id int [ref: > client.id]
  membership_id int [ref: > membership.id]   // по какой карте прошли
  entered_at datetime
  left_at datetime
}

Table trainer {
  id int [pk]
  full_name varchar
  status varchar          // active / dismissed — уволенных не удаляем
}

Table workout_type {      // справочник видов
  id int [pk]
  name varchar
}

Table trainer_workout_type {   // разрешение M:N
  id int [pk]
  trainer_id int [ref: > trainer.id]
  workout_type_id int [ref: > workout_type.id]
}

Table hall {
  id int [pk]
  club_id int
  name varchar
  capacity int
}

Table workout {           // занятие в расписании
  id int [pk]
  workout_type_id int [ref: > workout_type.id]
  trainer_id int [ref: > trainer.id]
  hall_id int [ref: > hall.id]
  starts_at datetime
  capacity int            // не больше вместимости зала
  status varchar          // scheduled / cancelled
}

Table booking {           // запись на групповое занятие
  id int [pk]
  workout_id int [ref: > workout.id]
  client_id int [ref: > client.id]
  status varchar          // booked / cancelled / attended / no_show
  created_at datetime
  indexes {
    (workout_id, client_id) [unique]   // один клиент — одна запись на занятие
  }
}

Table personal_package {
  id int [pk]
  client_id int [ref: > client.id]
  trainer_id int [ref: > trainer.id]
  sessions_total int
  sessions_used int
  price decimal(10,2)
}

Table personal_slot {
  id int [pk]
  package_id int [ref: > personal_package.id]
  trainer_id int [ref: > trainer.id]
  starts_at datetime
  status varchar          // booked / done / cancelled / no_show
  indexes {
    (trainer_id, starts_at) [unique]   // защита от двойной продажи слота
  }
}
Чего в DBML не видно. Уникальность «одна активная карта на клиента», лимит 30 дней заморозки в году, «вместимость занятия ≤ вместимости зала» — это ограничения и правила. Они живут в БД (частичные индексы, CHECK, триггеры) и в коде приложения, но на картинке ERD их нет — поэтому такие вещи обязательно выносят в текст постановки.

04Процессы: три готовые BPMN-схемы

ERD отвечает на вопрос «что храним», BPMN — «что и когда происходит». Ниже упрощённые схемы одного пула (система клуба); в полной версии клиент выносится отдельным пулом, а обмен идёт потоками сообщений.

◯ стартовое событие ◉ завершающее событие ▭ задача (глагол + объект) ◇ × XOR — ровно одна ветка ◯ ⏱ событие-таймер

Стартовое событие названо фактом, задачи — глаголами в инфинитиве, у каждой ветки XOR подписано условие, и финалов два: у «оплата отклонена» свой смысл, его нельзя схлопывать в общий «Конец». В базе успешная ветка создаёт строку membership — со снимком цены и условий из membership_type.

Три вещи, за которые тут снимают баллы. Первая: «подождать неделю» рисуют задачей — но ждать не работа, это событие-таймер. Вторая: счётчик «третья подряд» негде хранить, если в модели нет booking.status со значением no_show. Третья: у процесса один общий финал вместо трёх осмысленных исходов.

05Что меняется в базе: семь ситуаций из жизни клуба

Самая полезная проверка модели — прогнать через неё реальные события. Ниже: что происходит, как ломается наивное решение и что спасает правильное. Раскрывайте по одной.

Кейс 1. Увольняется тренер Марк

Администратор: «Марк уволился с 1 сентября. Уберите его из системы».

На Марка завязано многое: тридцать прошедших занятий, две записи на будущее, восемь оплаченных пакетов персоналок и записи в trainer_workout_type.

Наивное решение: DELETE FROM trainer WHERE id = 3 Если внешние ключи настроены на каскад — вместе с Марком исчезнут занятия, а с ними записи клиентов и вся история посещений. Если на SET NULL — останутся занятия-сироты без тренера. Если ограничение строгое — база просто не даст удалить, и администратор придёт с вопросом «почему не работает».
Правильно: мягкое удаление UPDATE trainer SET status = 'dismissed'. История цела, отчёты за прошлые месяцы не меняются, а приложение перестаёт показывать Марка в списках выбора. Внешние ключи — ON DELETE RESTRICT: физически удалить тренера с историей нельзя, и это правильно.

А что с будущими занятиями и пакетами?

Это уже не вопрос модели, а вопрос к заказчику — и именно так его надо задать: «При увольнении тренера его будущие занятия отменяются или передаются другому? Что происходит с оплаченными пакетами персоналок — возврат, перевод на другого тренера или доработка?» Пока ответа нет, решение фиксируется в допущениях.

Приём переносимый: сущности с историей не удаляют физически. Клиент, тренер, товар, сотрудник — всё это получает статус, а не DELETE.
Кейс 2. Клуб поднял цену безлимита с 4 000 до 5 000 ₽

Владелец: «С понедельника новая цена. Но у тех, кто уже купил, ничего не меняем».

Меняется одна строка — в справочнике membership_type. Ранее проданные карты не трогаются вообще: в каждой лежит своя цена, зафиксированная при покупке.

Как ломается модель без снимка Если цены нет в карте и сумма всегда берётся из справочника, то в понедельник у Ивана «задним числом» подорожает уже оплаченная карта. Возврат посчитается от 5 000 вместо 4 000, а бухгалтерия получит расхождение с кассой.
Тот же приём вы уже видели: тариф поездки в каршеринге, цена блюда в доставке, цена билета в кинотеатре. Формулировка-маркер всегда одна: «даже если потом изменили».
Кейс 3. Клиент не пришёл третий раз подряд

Правило: «После трёх неявок подряд блокируем запись на неделю».

Событие затрагивает три места: статус записи, счётчик неявок и — если это третья — блокировку с датой снятия.

Где хранить блокировку — два варианта, оба принимаются на защите. Вычислять на лету (посмотреть три последние записи клиента) — нет лишних данных, но запрос на каждую попытку записи. Хранить явно (booking_ban с датой окончания) — быстро и видно в интерфейсе, но требует аккуратного снятия по таймеру.

Что нельзя Хранить у клиента одно поле no_show_count и увеличивать его. Слово «подряд» тогда теряется: пришёл на занятие — счётчик должен обнулиться, а по одному числу непонятно, когда именно это произошло.

Администратор: «Кроссфит в четверг отменяем, там было 14 записей».

Одна строка занятия и четырнадцать строк записей. Ключевая тонкость: это не неявка клиентов — виноват клуб, поэтому санкции применять нельзя.

Частая ошибка проектирования Один общий статус cancelled без указания, кто отменил. Через месяц никто не ответит на вопрос «сколько занятий сорвал клуб» — а это ключевая метрика качества сервиса. Решение: либо отдельный статус cancelled_by_club, либо поле cancel_reason.

Кейс 6. Клиент требует удалить свои персональные данные

Юрист: «Пришло заявление на удаление персональных данных. Удаляйте».

Конфликт двух требований: закон требует убрать персональные данные, бухгалтерия — сохранить финансовые операции и посещения за отчётный период.

Решение: анонимизация вместо удаления Персональные поля затираются, а строка и все её связи остаются: full_name = 'Удалённый клиент #4821', phone = null, email = null, status = 'deleted'. Продажи, посещения и записи сохраняются, но за ними больше нет человека.

Кейс 7. Два клиента жмут «Записаться» на последнее место одновременно

Из жизни: на кроссфит осталось одно место, две заявки приходят с разницей в 20 миллисекунд.

Обе транзакции читают «занято 19 из 20», обе делают вывод «место есть», обе создают запись. В зале появляется 21-й человек — ровно та боль, из-за которой заказчик и пришёл.

Почему проверка «если мест меньше вместимости» не спасает Между чтением количества и вставкой записи проходит время. На уровне изоляции Read Committed (по умолчанию в PostgreSQL) вторая транзакция просто не видит ещё не закоммиченную запись первой. Это называется гонкой, и «проверить перед вставкой» её не лечит.
Три рабочих способа 1. Заблокировать строку занятия на время записи: SELECT … FROM workout WHERE id = 77 FOR UPDATE — вторая транзакция ждёт и видит уже актуальную картину.
2. Уровень изоляции Serializable — база сама отклонит конфликтующую транзакцию, но приложение обязано уметь её повторить.
3. Заранее создать строки-места (как кресла в кинотеатре) и повесить уникальность — конфликт станет физически невозможен.

А вот двойная продажа слота персоналки лечится проще всего, третьим способом: уникальный индекс на пару (trainer_id, starts_at). Вторая вставка упадёт с ошибкой при любом уровне изоляции, и приложение покажет «слот уже занят».

Правило для защиты: сначала назовите аномалию (потерянное обновление, фантом), потом выбирайте инструмент — ограничение, блокировку строки или уровень изоляции. Начинать с «поднимем изоляцию» — почти всегда дороже и слабее, чем поставить unique.

Как проверить свою модель за пять минут

  1. Возьмите каждое требование из блокнота и найдите на схеме место, где оно живёт. Не нашли — модель неполна.
  2. Прогоните через модель события: покупка, вход, запись, неявка, отмена, увольнение, рост цен. Каждое должно быть выразимо.
  3. Для каждого «удалить» спросите: а что станет с историей?
  4. Для каждого «сколько» спросите: а с какого момента считаем и что если задним числом?
  5. Выпишите всё, что решили сами, в раздел «Допущения». Записанное допущение ошибкой не считается, молчаливое — считается.
